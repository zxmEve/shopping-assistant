# ADR-0005：只有确认是同一配置的报价，才能放在一起比价

- 状态：已采用
- 日期：2026-09-04
- 关联需求：CAT-01、CAT-02、CAT-03、CAT-04、SRC-02、REC-02

## 先说结论

Provider 返回的商品文字先被当作未经验证的原始数据。系统统一品牌、型号和容量写法，再逐项检查内存、硬盘、系统、成色和套装。只有关键字段完整且一致的报价才能进入最低价比较；字段冲突的直接拒绝，信息不足的交给人工复核。

## 为什么需要这个决策

三个平台可能用不同文字描述同一台电脑：

| Provider 写法 | 实际含义 |
|---|---|
| `32G`、`32 GB`、`32768MB` | 32GB 内存 |
| `1T`、`1TB`、`1024GB` | 1TB 存储 |
| `Win11 Pro`、`Windows 11 Professional` | Windows 11 Pro |
| `A-240 PRO`、`a-240-pro` | 同一个型号 |

这些差异应该被统一，否则同款报价会被拆开，无法比较。

但下面这些看起来很像，实际不能算同一个配置：

- 16GB 内存和 32GB 内存；
- 512GB SSD 和 1TB SSD；
- 全新机和翻新机；
- 单机和“电脑 + 扩展坞”套装；
- `A-240` 和 `A-240 Pro`；
- Provider 字段写 32GB，但标题写 16GB。

如果系统把它们错误合并，翻新机或低配机的价格可能成为“最低价”，随后影响预算判断、制度检查和用户确认。这比漏掉一个报价更危险。

## Product、Variant、Offer 为什么要分开

### Product：它是哪一款产品

只保存相对稳定的身份，例如品牌、完整型号和品类：`Aster A-240 Pro 笔记本`。

### Variant：这款产品的哪一种配置

保存会改变商品价值或适用性的配置，例如 CPU、内存、硬盘、系统、保修、成色和套装。

### Offer：谁以什么条件出售

保存 Provider、卖家、价格、库存、运费、交期和证据。

选择三层模型的原因是：同一个 Product 可以有多种 Variant，同一个 Variant 又可以由多个卖家提供不同 Offer。最低价应该比较“同一 Variant 的多个 Offer”，而不是比较标题相似的所有商品。

## 我们想达到什么效果

1. 不同平台的等价写法能够归到同一个 Product 和 Variant。
2. 内存、硬盘、成色、套装或型号后缀不同，不能合并为同一 Variant。
3. 系统明确给出匹配结果、置信度、冲突字段、原因和证据。
4. 低置信度报价不参与最低价、最快交付和综合最优排序。
5. 即使 LLM 判断“这是同款”，服务端仍能拒绝关键字段冲突。
6. 被拒绝或待复核的报价仍保留在 UI 和 Trace 中，用户能看见为什么不能比较。

## 比较过的做法

| 做法 | 好处 | 为什么没有选择 |
|---|---|---|
| 直接相信 Provider 给出的商品 ID | 实现简单 | 不同 Provider 的 ID 体系不同，也不能证明关键配置一致 |
| 只按标题完全相同分组 | 几乎不会错合 | `32G` 与 `32 GB` 会被拆开，漏掉大量可比报价 |
| 只用标题相似度或向量搜索 | 能找到很多候选 | 相似标题可能吞掉 RAM、SSD、Pro 后缀、成色和套装差异 |
| 完全交给 LLM 判断 | 能理解复杂自然语言 | 结果可能波动，难以回放；模型错误会直接污染价格比较 |
| 规则统一字段，服务端检查冲突，不确定项人工复核 | 当前 P0 可解释、可测试、安全 | 覆盖的新写法有限，需要持续扩充别名和标注集 |

## 最终选择及原因

### 1. Provider 先返回 `ProviderRawOffer`

Raw Offer 保存 Provider 的原始标题和字段，不允许 Provider 直接声明系统内部可信的 Product ID 或 Variant ID。

为什么：外部平台只能提供原始事实，不能替系统决定“它和哪个商品完全相同”。这样也能保留问题现场，方便后来审计解析错误。

### 2. 结构化字段和标题分别解析，再互相核对

例如 Provider 的 `ram` 字段写 32GB，系统还会从标题中读取 RAM。如果两边分别写 32GB 和 16GB，就标记 `ram_gb` 冲突。

为什么：只相信其中一边会掩盖 Provider 数据错误。两份来源一致时置信度更高，互相矛盾时应该停止。

### 3. 先统一表达方式，再比较值

系统统一大小写、空格、连字符、容量单位和操作系统别名。例如 `1T` 与 `1024GB` 都变成整数 1024。

为什么：字符串不同不一定代表商品不同。先统一表达，才能避免把真正同款错误拆开。

### 4. 完整型号后缀和关键配置采用精确检查

RAM、存储、操作系统、成色、套装以及型号中的 `Pro` 等关键后缀发生冲突时，服务端拒绝合并。

为什么：这些字段会改变价格或是否满足需求，不能用“标题总体很相似”覆盖局部差异。

### 5. 匹配结果分为三种

| 结果 | 白话解释 | 是否参与比价 |
|---|---|---|
| `MATCH` | 关键字段完整且一致，确认可以比较 | 是 |
| `REVIEW_REQUIRED` | 没有发现明确冲突，但缺少关键事实或置信度不足 | 否，等待人工复核 |
| `REJECTED` | 已发现型号或关键配置冲突 | 否，服务端拒绝合并 |

为什么不直接使用“匹配/不匹配”两个结果：缺信息和明确冲突不是同一种问题。缺信息可以通过补证据解决，冲突则应该明确拒绝。

### 6. 置信度只表示“当前证据有多完整、一致”

当前分数来自关键字段覆盖率，以及 Provider 字段与标题是否同时给出相同答案。自动进入比价的门槛是 0.90。

为什么：系统需要一个明确边界把可比报价和待复核报价分开。

重要说明：当前 0.90 是 Fixture 阶段的工程门槛，不是经过真实商城数据校准的概率，也不表示“99% 一定匹配”。生产版本必须使用更大的人工标注集重新校准。

### 7. LLM 可以提出候选，但不能通过最终检查

未来可以让 LLM 或向量检索帮助寻找“可能是同款”的候选；最终是否允许合并，仍由服务端按关键字段检查。

为什么：LLM 擅长处理新别名和模糊描述，适合提高候选召回；确定性代码擅长做精确比较，适合守住价格和采购安全边界。两者不是互相替代，而是分工。

### 8. 不可比报价仍返回给推荐层和 UI

`OfferMatchAssessment` 保存原始报价、判断结果、冲突字段、原因和证据。推荐排序只接收 `MATCH`，UI 另外展示被拒绝或待复核的报价。

为什么：直接丢弃会让用户误以为 Provider 没有返回这条报价，也不利于定位解析问题和积累人工标注。

## 实际调用过程

```text
Provider 原始报价
  -> 统一容量、系统、大小写和标点
  -> 找到可能的 Product
  -> 根据关键配置建立 Variant 候选
  -> 服务端逐项检查冲突和缺失
  -> MATCH：生成可比 Offer
  -> REVIEW_REQUIRED：保留证据，等待人工复核
  -> REJECTED：记录冲突，拒绝合并
  -> 推荐服务只对 MATCH 计算金额、制度和排名
```

## 为什么优先保证 Precision，而不是 Recall

- Precision 关心：“系统说是同款的报价里，有多少真的同款？”
- Recall 关心：“所有真实同款报价里，系统找回了多少？”

采购比价中，低 Recall 会漏掉一些选择；低 Precision 会把错误商品加入比较，制造虚假最低价。后者会继续污染预算、Policy 和确认结果，因此本阶段优先保证 Precision。

这也是为什么 false merge——把不同商品错误合并——是一票否决指标，而低置信度候选会进入人工复核，不会被强行比较。

## 这项决策带来的代价

- 新 Provider 表达超出当前别名规则时，可能进入人工复核；
- Precision 优先会牺牲一部分 Recall；
- 成色、套装和型号规则需要按品类维护；
- UI 和数据模型要同时保存可比报价与不可比报价；
- 生产版本仍需要人工复核队列和更大标注集。

我们接受这些代价，因为“诚实地说无法确认”比“用错误商品得出最低价”更安全。

## 测试如何证明它有效

当前有 450 条常规 Raw Offer 和 9 条人工标注 hard cases，覆盖：

- `32G/32 GB/32768MB` 等价表达；
- `1T/1024GB/1TB` 等价表达；
- Windows 名称、品牌、型号的大小写和标点差异；
- 同型号不同 RAM；
- 同型号不同 SSD；
- 新品、翻新和二手；
- 单机和扩展坞套装；
- 高度相似但缺少关键型号后缀；
- Provider 字段和标题冲突；
- 缺失关键存储规格；
- 上游故意提出错误 Variant。

评测结果：

- Product match precision：100%；
- Variant match precision：100%；
- hard false merge：0；
- 冲突否决：2；
- 待人工复核：1；
- 9 条 hard cases 中自动验证 6 条，verified candidate rate 为 66.67%。

66.67% 不是“系统只识别对了三分之二”，而是测试集故意放入 2 条冲突数据和 1 条缺失数据；这些数据正确结果本来就不应该自动通过。

## 当前限制

- 只覆盖笔记本电脑和当前 Fixture 表达；
- 9 条 hard cases 太少，100% precision 不能外推为真实商城准确率；
- 当前没有 hybrid retrieval、LLM pairwise matcher 或开放世界别名召回；
- 置信度没有在真实人工标注集上做分桶校准；
- 尚未建设真正的人工复核工作队列；
- 真实 Provider 的字段缺失、语言混合和 schema drift 仍需单独验证。

## 术语对照

- Canonicalization / 归一：把不同写法转换成统一表达。
- Product：品牌和完整型号层面的产品。
- Variant：某个 Product 的具体配置。
- Offer：某个卖家的具体报价。
- Precision：被系统判为同款的结果中，真正同款的比例。
- Recall：所有真正同款结果中，被系统找回的比例。
- False merge：把不同 Product 或 Variant 错误合并。
- Hard case：专门设计来暴露错误合并的困难测试样本。
- Veto / 一票否决：只要出现一次就阻止发布的严重错误。
