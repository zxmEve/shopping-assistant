# ADR-0006：用明确的状态路线和执行额度约束采购任务

- 状态：已采用
- 日期：2026-09-04
- 对应需求：OPS-01、OPS-02、OPS-03、OPS-04、SRC-04

## 一句话结论

采购任务不能靠代码在各处直接改状态，也不能等工具调用完才检查是否超额。所有状态变化统一交给 Harness 校验；每个任务保存自己的额度和用量；工具在执行前占用额度，并按工具规则执行超时、有限重试、熔断和并发限制。

## 原来有什么问题

原来的 `run.state = ...` 分散在业务代码中。任何新代码都可能跳过追问、复核或用户确认，直接进入创建草稿，而且系统不会留下完整的状态变化历史。

原来的“预算”实际上只是数 Trace 和 TOOL 事件。它有三个问题：

1. Trace 是执行记录，不是执行额度；多记一条说明不应该减少一次业务调用机会。
2. 没有区分状态变化、Agent 回合、逻辑工具调用、Provider 请求和重试。
3. 超时、重试和熔断没有统一入口，故障只会由业务代码临时处理。

这会让系统看起来有 Harness，但无法回答“为什么允许这次状态变化”“本次任务还剩多少额度”“这个 Provider 为什么没有继续调用”。

## 我们怎么做

### 1. 状态只能走规定路线

Harness 保存一张允许迁移表。例如：

```text
COLLECTING -> WAITING_USER -> COLLECTING
COLLECTING -> SOURCING -> REVIEWING -> WAITING_CONFIRMATION
WAITING_CONFIRMATION -> REVALIDATING
REVALIDATING -> WAITING_CONFIRMATION（报价变化）
REVALIDATING -> DRAFT_CREATING -> DRAFT_CREATED
```

失败可以从仍在处理的阶段进入 `FAILED`，完成和失败状态不能再向前推进。

为什么这样选择：采购流程中的确认和写入顺序是安全规则，不是模型建议。把路线集中在 Harness 后，业务代码即使写错目标状态也会被拒绝。

### 2. 每次变化都增加版本并保存事件

每次合法变化都会：

- `state_version` 加一；
- 追加一条 `state_events`；
- 记录原状态、目标状态、原因、操作者和时间；
- 同时写入 Trace，方便前端展示。

为什么同时保存版本和事件：当前状态告诉我们“现在在哪”，事件告诉我们“怎么走到这里”。连续版本还能发现历史缺失或顺序错误。

### 3. 每个 Run 保存自己的额度和用量

创建 Run 时，Harness 把当时的配置复制到 Run。当前保存：

- 最多 20 次状态变化；
- 最多 12 个 Agent 回合；
- 最多 12 次逻辑工具调用；
- 最多 12 次 Provider 请求；
- 最多 4 次重试；
- 最多 25 秒在线执行时间；
- 最多 4 个并行 Provider；
- 输入 token、输出 token 和模型费用上限。

为什么复制到 Run：如果明天修改全局配置，仍然能解释昨天的任务是按什么限制运行的。额度不能只存在进程配置里。

这里的在线执行时间只累计 Agent、工具调用和重试退避实际占用的时间。等待用户回复不计时，否则用户阅读推荐或补充需求的正常停留会被误判成系统超时。

### 4. 先扣额度，再执行动作

状态变化、工具调用和重试都在真正执行前检查额度。额度不足时保持当前状态，写入 `budget.exceeded`，返回已保存的状态和 Trace。

为什么必须在动作前：写入发生后再报告超额，已经无法撤销副作用。前置检查才能保证“超限就没有执行”。

### 5. 故障策略属于工具，不属于 Prompt

每个工具策略声明超时时间、最多尝试次数、退避时间和熔断阈值。Provider 调用还经过并发信号量。429、5xx 和 timeout 可以有限重试；连续失败达到阈值后打开该工具与 Provider 的独立熔断器，不影响其他来源。

为什么按“工具 + Provider”隔离：一个商城不可用时，内部目录和其他商城仍应返回结果。如果用一个全局熔断器，单个来源故障会错误停止整个采购任务。

## 计数口径

- 逻辑工具调用：用户意图上的一次工具动作，只计一次。
- Provider 请求：每次真实尝试都计数，包括重试。
- 重试：第一次失败后的再次尝试；首次调用不算重试。
- 状态变化：只有通过允许迁移表并真正改变状态才计数。
- Trace：只负责记录，不再被当作预算。

明确口径是为了避免通过“少写 Trace”规避预算，也避免重试被隐藏在一次工具调用里。

## 测试如何证明它有效

- 正常采购闭环只能走完整合法路线，状态版本从 1 连续递增；
- 跳过安全阶段直接创建草稿会被拒绝，Run 不发生变化；
- 状态额度耗尽后，下一次变化在执行前停止；
- 时间额度耗尽后，不再占用工具额度；
- 用户停留后继续任务不会消耗在线执行时间；
- 429 首次失败后可以重试成功，并分别记录工具、Provider 和重试用量；
- 工具超时达到阈值后打开熔断器，下一次调用不会执行；
- 四个 Provider 任务并发时，实际同时执行数不会超过配置值；
- Run 经 JSON 保存和重新加载后，状态历史与预算用量不丢失。

## 当前边界

- 当前 OpenAI Agent 只是规划器，尚未回传真实 token 和费用；Harness 已提供额度与记账入口，但不能把未观测到的数据写成真实用量。
- 当前熔断器和并发信号量是单进程内存状态，多实例共享熔断需要 Redis 或网关支持。
- JSON Repository 会保存状态历史，但还没有数据库乐观锁、独立 checkpoint、pause/resume/cancel；这些属于下一纵向切片。
- 通用超时/重试包装器已经用于异步 Provider 报价读取；同步企业规则和本地草稿创建仍是确定性进程内调用，不宣称已经具备外部服务级故障恢复。
- 目前没有完整 cassette，故障可通过 Fixture 场景复现，但还不能回放真实模型和外部工具轨迹。

## 术语对照

- 状态机：规定任务允许处于哪些阶段，以及阶段之间怎样移动。
- 执行预算：一次任务最多可以消耗多少步骤、调用、时间、token 或费用。
- 重试：暂时失败后再次尝试，但有明确次数上限。
- 熔断：某个来源连续失败后暂时停止调用，避免继续浪费资源。
- Bulkhead / 并发隔离：限制同时调用外部来源的数量，避免一个环节拖垮整个进程。
