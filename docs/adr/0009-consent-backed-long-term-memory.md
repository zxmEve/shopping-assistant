# ADR-0009：长期记忆必须由用户看得见、改得了、删得掉

- 状态：已采用（M4 第一片）
- 日期：2026-09-04
- 对应里程碑：M4 长期记忆与 RAG

## 一句话结论

Agent 不能因为用户说过一句话就自动永久保存。创建长期记忆必须有本次明确同意；个人记忆只给本人，团队记忆只给同租户同团队；只有创建者能修改或删除，并保留不含隐藏推理的变化审计。

## 为什么要先做权限和删除，再做“智能记忆”

自动提取记忆很容易做出演示效果，但一旦保存范围不清楚，后面再加权限会很危险：一次采购的临时要求可能被误当成长期偏好，个人习惯可能被团队成员看到，错误信息也可能持续影响后续推荐。

所以顺序是：先证明用户能控制数据，再让模型提出记忆候选。模型以后可以建议“这句话可能值得记住”，但不能绕过同意接口直接写库。

## 四种记忆是什么

- Profile：个人长期偏好，例如“开发机至少 32GB”；只对本人可见。
- Episodic：个人过去事件的摘要，例如“上次采购因交期选择内部目录”；只对本人可见，并应有保留期限。
- Team：团队共享标准，例如“研发组默认三年保修”；同租户同团队可见。
- Semantic：经过治理的知识或制度事实；普通用户 API 禁止创建，正式内容只能由下一片的版本化制度文档导入。

四种类型共用一张表，是因为当前的授权、修改、删除、版本和审计规则相同；`scope` 明确区分用途，检索时不能混用。

## 为什么团队成员能读但不能随便改

“同团队可见”不等于“同团队都能改”。如果任何成员都能覆盖团队标准，来源和责任会变得不清楚。第一片采用最保守规则：创建者拥有修改和删除权，其他团队成员只读。后续接企业角色后，可以增加经过审计的团队管理员权限。

## 为什么使用软删除

用户删除后，正常查询立即看不到记录，主记录中的正文会被清除；数据库只保留删除状态和不含正文的最小审计，用于证明系统执行过删除并调查越权修改。审计接口只对原创建者开放。

生产环境还要定义物理清除周期，并让向量索引、缓存和备份同步删除。当前没有向量副本，因此本片先验证主记录的删除语义。

## 为什么修改需要版本号

用户可能同时打开两个页面。较旧页面如果直接保存，会覆盖较新修改。客户端提交它读到的 `expected_version`；数据库版本不同就拒绝，让客户端重新加载。这和 Run 的乐观锁是同一个原则。

## 当前验证

- API 没有 `consent_acknowledged=true` 时拒绝创建；
- 个人记忆不能被同团队其他用户或其他租户读取；
- 团队记忆只对同租户同团队可见；
- 普通用户不能把自己写的内容伪装成 Semantic 制度知识；
- 非创建者不能修改团队记忆；
- 旧版本修改被拒绝；
- 创建、修改、删除产生连续审计事件；
- 第二个 Alembic migration 和完整生命周期已在真实 PostgreSQL 17 运行。

## 当前限制

- 当前“同意”是 API 中一次明确确认并生成 consent ID，还没有独立的同意撤销策略表；
- 尚未从采购对话自动生成“待确认的记忆候选”；
- 尚未设置 Episodic 自动过期和物理清除任务；
- 当前表仍保留 Semantic 兼容类型，但目标设计将制度文档迁入独立 Knowledge Base；它不能作为 Policy 最终证据，详见 `12-memory-context-technical-design.md`；
- 尚未建立向量和全文索引，RAG 是下一片。

## 术语对照

- Consent：用户明确允许保存这条长期信息。
- Scope：这条记忆属于个人、团队、事件还是知识。
- Soft delete：正常使用中已删除，但保留受限审计所需记录。
- Audit：记录谁在什么时候创建、修改或删除了什么。
