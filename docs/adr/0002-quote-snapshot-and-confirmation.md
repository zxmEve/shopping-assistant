# ADR-0002：用户确认后，创建草稿前必须重新检查报价

- 状态：已采用
- 日期：2026-09-04
- 关联需求：HITL-01、HITL-02、HITL-03、HITL-04、HITL-05

## 先说结论

用户确认的不是一个永远有效的“创建草稿”按钮，而是某个需求版本下的一组具体报价事实。系统在真正创建草稿前必须重新读取报价并检查预算、制度、供应商和权限；如果重要事实变化，就停止创建，展示差异并要求用户再次确认。

## 一个具体例子

用户看到的推荐是：

- 单价 7,800 元；
- 有 30 台库存；
- 7 天送达；
- 总额在预算内。

用户离开页面十分钟后再点击确认。此时商品可能涨到 8,200 元，库存可能只剩 5 台，供应商也可能变成待审核状态。

如果系统仍按旧页面创建草稿，就会产生两个问题：

1. 草稿内容不是用户刚才同意的内容；
2. 旧的预算和制度结论可能已经失效。

所以，“推荐时检查过”不能替代“写入前再检查一次”。

## 我们想保护什么

- 用户只对自己实际看到的价格和条件负责；
- 旧页面、旧需求或别人的确认信息不能被重放；
- 同一个确认请求重复发送时，只产生一个草稿；
- 系统只创建 `DRAFT_NOT_SUBMITTED` 草稿，不提交审批，也不下单。

## 比较过的做法

| 做法 | 好处 | 风险 |
|---|---|---|
| 点击后直接使用页面里的报价 | 实现最简单 | 页面数据可以被修改，也可能已经过期 |
| 只给确认凭证设置 15 分钟有效期 | 能阻止很老的请求 | 15 分钟内价格仍可能变化，无法发现 |
| 把完整报价都放进确认凭证 | 校验时不必查数据库 | 凭证很大，会携带不必要的业务数据，而且仍不知道 Provider 当前事实 |
| 创建草稿前重新读取并比较 | 多一次查询，但事实最可靠 | 需要处理变化提示和第二次确认 |

## 最终选择及原因

### 1. 推荐时保存一份“报价快照”

报价快照是用户看到推荐时的重要事实副本，包括单价、运费、税率、库存、交期、来源、抓取时间、有效期和内容摘要。

为什么：后面重新读取报价时，需要知道“和什么比较”。如果只保存 offer ID，就无法准确告诉用户哪些字段发生了变化。

### 2. 给快照生成 fingerprint

Fingerprint 可以理解为这份快照的“内容指纹”：相同事实会生成相同字符串，只要任一重要字段变化，指纹就会变化。

为什么：确认凭证不必装下完整报价，只需要绑定固定长度的指纹；校验更简单，也减少信息暴露。

### 3. Action Token 同时绑定人、任务、需求版本、动作和报价指纹

Action Token 是短期确认凭证。它回答的不是“用户是谁”，而是“这个用户是否确认了这个任务、这个需求版本、这份报价以及创建草稿这个动作”。

为什么：

- 绑定用户和租户，能阻止跨用户使用；
- 绑定 run，能阻止拿到其他任务使用；
- 绑定需求版本，能阻止需求修改后继续使用旧确认；
- 绑定动作，能阻止把“创建草稿”的确认拿去做其他操作；
- 绑定报价指纹，能阻止报价变化后继续使用旧确认。

### 4. 创建草稿前重新读取事实

系统重新读取当前 Offer，并重新计算金额，再检查预算、制度、供应商和权限。

为什么：模型的解释和旧缓存都不能代表当前事实；最终写入必须依赖服务端重新取得的数据和确定性规则。

### 5. 事实变化时停止，而不是自动接受新价格

系统返回字段级差异，例如“单价 7,800 → 8,200”，更新页面并签发新的 Action Token。旧 Token 立即失效。

为什么：即使新价格仍在预算内，也不能替用户默认接受。用户确认必须建立在知情基础上。

### 6. 重复确认使用同一个业务键

业务键由 run、offer 和需求版本生成。相同确认即使请求发送多次，也返回同一草稿。

为什么：浏览器重试、网络超时和用户连续点击都很常见，不能因此创建多个采购申请。

## 实际调用过程

```text
生成推荐
  -> 保存报价快照
  -> 生成快照指纹
  -> 签发 Action Token
  -> 等待用户确认
  -> 重新读取当前报价
  -> 重新计算金额并检查制度/预算/供应商/权限
  -> 没变化：创建一个未提交草稿
  -> 有变化：不创建，展示差异，要求再次确认
```

## 为什么这些判断不能交给 LLM

LLM 可以解释“价格为什么变化”或帮助组织提示语，但不能决定两个金额是否相同、Token 是否属于当前用户、旧确认是否仍有效，也不能绕过预算和制度。这里涉及金额和写入副作用，必须由服务端代码做精确比较。

## 这项决策带来的代价

- 确认路径多一次 Provider 查询，延迟和调用成本略有增加；
- UI 必须展示变化，而不是简单显示成功或失败；
- 需要保存报价快照和新的确认状态；
- Provider 暂时不可用时，系统宁可不创建草稿。

这些代价是有意接受的，因为“稍慢但确认事实正确”比“快速生成错误草稿”更重要。

## 测试如何证明它有效

- 修改 Fixture 报价后，第一次确认不会创建草稿；
- 返回的变化列表至少包含单价和证据内容变化；
- 系统签发新 Token，旧 Token 再次提交会被拒绝；
- 使用新 Token 后才能创建草稿；
- 连续并发确认十次，最终只出现一个草稿写入事件；
- 草稿状态始终为 `DRAFT_NOT_SUBMITTED`。

## 当前限制

- 当前锁只保护单个 Python 进程；多实例部署还需要数据库唯一约束和条件更新；
- 目前对报价变化有字段差异，预算、制度和供应商变化还没有同等完整的差异展示；
- Fixture Token 不是生产登录方案；生产环境仍需真实 SSO、密钥轮换和安全审计。

## 术语对照

- 报价快照：用户看到推荐时的重要事实副本。
- Fingerprint：由快照内容生成的固定长度摘要，用来判断事实是否变化。
- Action Token：绑定具体人、任务、事实和动作的短期确认凭证。
- 幂等：同一业务请求重复执行，最终只产生一次业务效果。
- TOCTOU：检查事实和使用事实之间存在时间差；本 ADR 解决的正是这个问题。
