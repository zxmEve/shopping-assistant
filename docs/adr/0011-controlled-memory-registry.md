# ADR-0011：记忆的 Key、品类和标签由受控 Registry 提供

- 状态：已采用
- 日期：2026-09-08
- 影响范围：长期记忆 API、数据库字段、ContextAssembler、Consent、测试

## 决策

用户和模型不能自由创建正式的 `memory_key`、品类或 Tag。

当前版本把定义放在版本控制中的 `memory_registry.yaml`。用户保存的是某个已登记 Key 对应的结构化值；数据库同时记录定义版本、稳定品类 ID、正式 Tag ID、来源、有效期和同意记录。

Registry 更新必须经过代码评审、自动测试和部署。将来接企业 PIM/ERP 后，可以由受治理的同步任务生成 Registry 新版本，但普通对话和普通用户 API 仍不能直接发布定义。

## 为什么这样决定

如果 Key 和品类完全由用户输入，会出现这些问题：

- `preferred_brand`、`favorite_brand` 和 `品牌偏好` 表示同一件事，却无法稳定查询；
- “电脑”可能表示全部计算机，也可能只表示笔记本，系统容易静默选错品类；
- 模型临时生成的 Tag 会不断增长，无法用于可靠过滤；
- 同一个 Key 可能一会儿保存字符串，一会儿保存数字，代码无法安全使用；
- Agent 可能通过自造 Key 绕过原本的上下文投影边界。

受控 Registry 给每种记忆一个明确的数据格式、适用品类、允许 Scope 和允许使用它的 Agent。这样错误会在写入时被拒绝，而不是等到模型调用时才暴露。

## 为什么当前使用 YAML，而不是可在线编辑的数据库表

项目目前只有一个笔记本品类，没有企业 PIM/ERP 主数据源。版本化 YAML 更容易审查、回滚、写测试和在面试 Demo 中复现，也不会意外提供一个“普通用户修改系统词汇”的入口。

数据库保存用户记忆值和 Consent；Registry 定义由部署版本提供。等接入真实主数据系统后，再增加受治理的同步表和发布流程，而不是让后台页面直接修改生产定义。

## 品类别名怎么处理

别名可以多对一，例如 `laptop`、`notebook`、`笔记本` 都映射到稳定 ID `CAT-COMPUTER-LAPTOP`。

同一个词如果映射多个品类，例如当前 Registry 中的“电脑”，解析接口返回歧义错误，不会静默选择。调用方需要提供更具体的词或让用户确认。

## Tag 怎么处理

API 可以接收正式 Tag ID、标准 code 或已登记别名。服务端统一转换成正式 Tag ID 后再写数据库。无法映射的自由 Tag 会被拒绝。

Tag 目前用于：

- 验证它是否适用于当前品类；
- 作为 Agent 上下文中的结构化提示和 Trace 元数据；
- 为后续全文/向量检索提供前置过滤条件。

Tag 不授予数据权限，也不能覆盖 Scope、tenant、owner 或团队边界。

## Consent 与幂等

每次正式创建记忆同时写入一条 Consent，记录用户看到的文字、用途、策略版本和 `request_id`。同一 `request_id` 重试返回同一记忆；如果换了请求内容，则返回冲突，防止一个确认凭证被复用于另一条记忆。

同一用户、Scope、Key 和品类收到新的确认请求时，新记录变为 ACTIVE，旧记录标记为 SUPERSEDED。历史审计不复制记忆正文。

## 当前限制

- Registry 仍是项目内 fixture，还没有从企业 PIM/ERP 自动同步；
- Tag 已保存为正式 ID 数组，尚未拆成独立关联表；
- 当前实现支持正在使用的 `REPLACE` 和 `KEEP_LATEST`，集合合并和人工冲突工作流留到后续版本；
- Consent 已可查询，但撤回、物理清除和候选接受流程属于 M2.3。

## 验收证据

- 自由 Key、错误结构化值、错误 Scope 和未知 Tag 都会在写入前被拒绝；
- 歧义品类别名不会静默解析；
- 普通员工不能写 TEAM 记忆；
- Consent 与记忆在同一事务写入，并通过请求指纹实现幂等；
- 新确认版本会替代旧版本；
- 过期和未生效记忆不会进入列表或 Agent 上下文；
- 当前后端回归测试为 103/103 通过。
