# ADR-0001：用“需求—实现—证据”判断项目是否真的完成

- 状态：已采用
- 日期：2026-09-04

## 先说结论

我们不再用“代码写了多少”或“测试通过率很高”判断功能是否完成。每项需求都必须同时回答三个问题：要求是什么、代码在哪里、什么证据证明它满足要求。缺少任何一项，都不能标记为“已验证”。

## 当时遇到的问题

这个项目同时有远期规划、当前代码、实现报告和评测报告。它们表达的时间范围不同：规划描述最终想做什么，代码只代表今天已经做了什么。

如果把两者写在一起，会出现几个误解：

- README 写了长期记忆，读者可能以为长期记忆已经实现；
- 20 个简单场景全部通过，读者可能以为所有 P0 需求都通过；
- 有一个测试叫“商品匹配”，但它只检查内存过滤，名称会夸大真实覆盖；
- 后来的人只看到绿色测试，不知道哪些高风险情况根本没有测试。

这对面试项目尤其危险：功能数量很多，但任何一个无法由代码和报告复现的说法都会降低可信度。

## 我们想达到什么效果

1. 任何“已经完成”的说法都能找到代码和验收证据。
2. 未来计划与当前能力明确分开。
3. 金额、权限、租户隔离等严重错误不能被其他高分掩盖。
4. 新成员能看懂为什么做出重要设计选择，而不只是看到最终代码。

## 比较过的做法

| 做法 | 好处 | 为什么没有选择 |
|---|---|---|
| 只维护开发任务列表 | 简单，更新快 | “任务完成”不等于验收标准满足，也看不到测试证据 |
| 只看测试通过率 | 数字直观，适合 CI | 测试可能覆盖错了内容；20/20 不代表所有需求完成 |
| 全部做完后再整理文档 | 开发初期负担小 | 设计原因、失败记录和真实边界很容易丢失 |
| 需求、实现和证据建立对应关系 | 状态更可信，便于复核 | 维护成本更高，但最符合本项目的展示目标 |

## 最终选择及原因

### 1. 产品需求文档只负责说明“要做到什么”

`docs/03-product-requirements.md` 保存需求和验收标准，不在这里声称当前已经实现。

为什么：需求应该相对稳定。如果它同时承担进度汇报，读者很难区分目标和事实。

### 2. 需求追踪矩阵负责说明“现在做到哪里”

`docs/08-requirements-traceability.md` 为每个需求记录状态、代码或测试证据，以及仍缺少什么。

为什么：这样可以从一个需求 ID 直接追到当前实现，避免在多份文档里猜测真实进度。

### 3. 只有实现和验收证据同时存在，才能标记为 `VERIFIED`

这里的 `VERIFIED` 意思是“已有实现，并且验收标准已经被自动化测试或明确的人工记录证明”。只有代码、没有足够测试时，只能标记为 `IMPLEMENTED`。

为什么：这能防止把“我写了一个类”误认为“这个业务能力已经可靠”。

### 4. 每个评测场景必须关联需求 ID

为什么：评测数量本身没有意义。只有知道每个场景在验证哪条需求，才能发现重复测试和覆盖空白。

### 5. 严重错误采用“一票否决”

金额计算错误、越权写入、跨租户泄漏、制度绕过、重复草稿和回放失败都属于一票否决项。只要出现一次，整次发布检查失败。

为什么：这些错误的影响不能用“其他 99 个场景表现很好”来抵消。例如发生一次跨租户泄漏，就不能因为推荐准确率高而发布。

### 6. README 只陈述当前事实

未来能力必须标记为“规划中”，Fixture、真实模型和真实 Provider 的结果必须分开描述。

为什么：README 是多数读者的第一入口，也是最容易产生过度承诺的地方。

### 7. 重要设计单独写 ADR

ADR 是“架构决策记录”，重点不是记录代码，而是记录当时的问题、考虑过的方案、选择理由和代价。

为什么：代码只能告诉我们“怎么做”，通常不能告诉我们“为什么没有选择另一个做法”。

## 这项决策带来的代价

- 每个功能切片都要同步更新需求状态、测试、报告和 ADR；
- 文档数字必须在测试变化后及时更新；
- 开发速度看起来会慢一点。

我们接受这些代价，因为这个项目要展示的正是可验证的 Agent 工程，而不是功能清单。

## 如何检查这项决策是否真正执行

- 场景文件中的每个场景都有 Requirement ID 或明确的验收引用；
- 需求追踪矩阵区分 `PLANNED`、`IMPLEMENTED` 和 `VERIFIED`；
- CI 同时运行代码检查、单元测试、确定性评测和前端构建；
- README 的测试数量与最新评测报告一致；
- 尚未实现的真实模型、长期记忆和生产能力仍明确标记为未完成。

## 这项决策不能保证什么

追踪矩阵只能保证“证据是否存在且名称诚实”，不能自动保证测试设计本身足够好。测试仍可能遗漏真实世界问题，因此每次新增高风险能力时，仍需要重新审查验收场景是否真的证明了需求。
