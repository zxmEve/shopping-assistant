# ADR-0012：长期偏好先生成候选，再由用户确认

- 状态：已采用
- 日期：2026-09-08

## 要解决的问题

用户不应该每次都手工填写记忆 Key 和 JSON，但系统也不能把一次采购要求、模型建议、价格、预算或凭证偷偷保存成长期记忆。

真正的风险不是“提取不够聪明”，而是错误内容一旦进入长期记忆，就会在后续任务中持续影响 Agent。

## 决策

系统把提取和保存拆成两步：

```text
已完成的采购 Run
  -> 只检查用户原话
  -> 生成可查看的 MemoryCandidate
  -> 用户接受 / 拒绝 / 不处理直到过期
  -> 接受后才创建 Consent 和 LongTermMemory
```

第一版提取器使用保守的确定性规则，只识别“以后、默认、记住、一直”等明确长期表达，并只生成 Registry 已登记的笔记本偏好。复杂句子宁可暂时不提取，也不猜测用户意图。

候选单独存表，不进入 Agent 上下文。它保存压缩后的建议、结构化值和用户消息引用，不复制整段聊天。用户接受时不能修改候选的 Key、Scope、值或来源；服务端会重新执行 Registry、权限和 Consent 校验。

## 为什么这样选择

1. **先候选后保存**：用户能看见系统准备记住什么，未确认内容没有长期影响。
2. **只读取用户消息**：助手建议和网页 Prompt Injection 不能变成用户偏好。
3. **只在草稿创建后提取**：采购主流程已安全完成，提取失败不会阻断采购。
4. **保守规则优先**：当前品类和 Key 数量很小，规则容易测试和解释；未来模型提取器仍必须输出同一候选结构，不能获得写权限。
5. **独立候选状态**：`PENDING/ACCEPTED/REJECTED/EXPIRED` 让 UI、审计和重试有明确依据。
6. **复用 Consent 幂等链路**：重复点击或处理中断不会创建两条长期记忆；变更已有偏好时仍走版本替代。
7. **PROFILE 优先**：普通员工自动提取只生成个人候选，避免一句“团队以后都这样”绕过 TEAM 管理权限。
8. **接受时再查冲突**：候选显示后如果已有记忆发生变化，旧候选不能覆盖新值，必须重新生成并确认。

## 被拒绝的方案

### 采购结束后自动写入

拒绝。它无法证明用户同意长期用途，也容易把单次要求升级成默认值。

### 让模型直接调用记忆写工具

拒绝。Prompt Injection、参数错误或误判会直接产生跨会话副作用，Harness 很难仅凭工具调用判断语义同意是否真实存在。

### 保存完整聊天作为记忆

拒绝。内容过长、包含无关实时事实和敏感信息，而且后续 Agent 难以稳定选择。

## 结果与限制

- 临时需求、助手文本、凭证、邮箱、手机号和银行卡信息不会生成候选；
- 精确重复已有记忆不会再次提示，值变化会明确标记将替换已有偏好；
- 候选 14 天未处理即过期；
- 当前只覆盖 Registry 中的笔记本 PROFILE 偏好；TEAM 候选审批、更复杂语言和 Consent 撤回/物理清除仍属于后续增强。
