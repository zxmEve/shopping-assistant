# ProcurePilot 架构决策导读

ADR 是“为什么这样设计”的记录，不是代码说明书。建议先看本页，再按你关心的问题阅读对应 ADR。

## 十三个决策解决了什么问题

| ADR | 它在防什么问题 | 为什么选择现在的做法 |
|---|---|---|
| [ADR-0001](0001-project-governance-and-delivery.md) | 把规划中的能力写成已经完成，或用绿色测试掩盖覆盖空白 | 用需求、实现和证据三者对应来判断是否真的完成；严重错误一票否决 |
| [ADR-0002](0002-quote-snapshot-and-confirmation.md) | 用户确认后价格、库存或制度变化，系统仍用旧事实创建草稿 | 确认时绑定用户看到的报价，写入前重新读取；变化后必须再次确认 |
| [ADR-0003](0003-fixture-session-and-tool-registry.md) | 客户端伪造身份，或 Agent 因 Prompt Injection 调用越权工具 | 身份由服务端确认；工具按角色明确允许，未登记工具默认拒绝 |
| [ADR-0004](0004-bounded-active-clarification.md) | Agent 一次问太多、漏问重要信息或无限追问 | 先问影响预算和候选的问题，每轮最多三问，最多三轮，并限制可使用的默认值 |
| [ADR-0005](0005-deterministic-product-canonicalization.md) | 把低配、翻新或套装商品错误合并，制造虚假最低价 | 统一不同写法后逐项检查关键配置；冲突拒绝，缺信息人工复核，只有确认同款才比价 |
| [ADR-0006](0006-explicit-state-machine-and-execution-budgets.md) | 状态可以被跳过，Trace 计数不能真正约束工具和 Provider 调用 | 状态统一走 Harness 迁移表；每个 Run 保存额度和用量；工具执行超时、有限重试、独立熔断和并发隔离 |
| [ADR-0007](0007-grounded-agent-function-tools.md) | Agent 只写计划，或通过工具参数虚构价格、预算和商品事实 | 给专家挂载严格只读工具；模型只选 Provider 和已查询报价 ID，其他事实由服务器读取 |
| [ADR-0008](0008-postgres-run-store.md) | JSON 文件无法安全支撑多进程并发、租户查询和唯一约束 | PostgreSQL 原子保存完整 Run，同时拆出消息和 Trace 供查询；每次读取带租户条件，旧版本写入和重复草稿由数据库拒绝 |
| [ADR-0009](0009-consent-backed-long-term-memory.md) | Agent 把一次性需求偷偷记住、把个人信息分享给团队，或让用户无法更正和删除 | 只有用户明确同意才创建；个人和团队记忆分开授权；只有创建者可改删；每次变化都留审计记录 |
| [ADR-0010](0010-explicit-server-orchestrated-multi-agent.md) | 把固定规则包装成多个 Agent，增加成本、延迟和不稳定性 | 只保留 Requirement/Sourcing 两个模型角色；路由、金额、制度、证据和写入使用确定性服务 |
| [ADR-0011](0011-controlled-memory-registry.md) | 用户或模型自由创造 Key、品类和 Tag，导致同义词混乱、结构不一致和上下文越界 | 定义来自版本化 Registry；用户只提交已登记 Key 的结构化值，歧义拒绝并保存 Consent |
| [ADR-0012](0012-reviewable-memory-candidates.md) | 系统把一次需求、助手建议或敏感内容自动升级成长期偏好 | 只从已完成任务的用户原话生成独立候选；用户接受后才复用 Consent 和幂等链路写入 |
| [ADR-0013](0013-versioned-policy-knowledge-fts.md) | 制度全文混入记忆或 Prompt，检索结果跨租户、过期或与可执行规则不一致 | 制度独立版本化发布；权限和生效期先过滤；FTS 返回引用；版本冲突安全停止 |

## 这些决策背后的共同原则

1. LLM 负责理解模糊语言和提出候选，不负责修改金额、权限、制度和事实。
2. 会影响金额或写入结果的判断，由服务端代码再次检查。
3. 外部输入默认不可信，包括用户提交的身份字段和 Provider 商品文字。
4. 不确定时停止或请求人工确认，不用“看起来可能正确”代替证据。
5. 功能是否完成由验收证据决定，不由文档措辞或类名决定。

## 推荐阅读顺序

如果想理解一条完整采购链路，建议按下面顺序阅读：

1. ADR-0004：系统怎样补齐采购需求；
2. ADR-0005：系统怎样判断哪些报价真的可比；
3. ADR-0003：系统怎样限制身份和工具；
4. ADR-0006：系统怎样限制状态、调用、重试和时间；
5. ADR-0007：Agent 怎样调用工具但不能改写采购事实；
6. ADR-0002：用户确认后怎样安全创建草稿；
7. ADR-0008：任务、消息和 Trace 怎样安全进入数据库；
8. ADR-0009：长期记忆为什么必须由用户控制；
9. ADR-0010：服务端怎样显式调度并约束多个独立 Agent；
10. ADR-0011：系统怎样控制记忆 Key、品类、Tag 和结构化值；
11. ADR-0012：系统怎样提取偏好但不偷偷写入长期记忆；
12. ADR-0013：制度知识怎样检索和引用，但不取代规则裁决；
13. ADR-0001：项目怎样证明以上能力真的完成。

## 状态说明

- 已采用：当前代码已经按该决策实现；
- 提议中：方案正在讨论，尚未成为稳定实现；
- 已替代：历史决策仍保留，但已经由新的 ADR 替换。

每份 ADR 的“当前限制”同样重要。“已采用”只表示当前实现遵循该设计，不表示它已经达到完整生产水平。
