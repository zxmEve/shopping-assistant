# ADR-0008：一条采购任务怎样安全存进 PostgreSQL

- 状态：已采用（M3 最小纵向切片完成）
- 日期：2026-09-04
- 对应需求：IAM-02、HITL-04、OPS-01、OPS-04

## 一句话结论

PostgreSQL 保存一份完整的采购任务快照，保证任务能够整体恢复；同时把消息和 Trace 拆成普通表，方便后续审计、长期记忆和 RAG 查询。每次查询都带租户和用户条件，每次更新都检查版本，草稿身份由数据库保证不重复。

## 为什么不能继续只用 JSON 文件

JSON Repository 很适合本地演示：不用启动数据库，文件也容易查看。但当两个服务进程同时修改同一任务时，它们可能先后覆盖彼此；按租户查询、查某条消息或统计工具调用也需要扫描整份文件；重复草稿只能依赖单个进程内的锁。

这些问题不是多写几个文件锁就能可靠解决的。长期记忆和 RAG 还要持续按租户检索消息与证据，因此先建立真正的数据库边界，再继续做记忆。

## 为什么既存完整快照，又拆出消息和 Trace

完整快照包含 Run 当前所需的全部业务数据。读取或恢复任务时只需要反序列化一个对象，领域模型增加字段也不必立即拆出许多新表。

消息和 Trace 的使用方式不同：它们会按时间、角色、工具和租户查询，也会成为记忆提取与评测的输入。如果只塞在一块 JSON 中，每次检索都要读取并解析整个 Run。所以一次保存会在同一个事务中完成三件事：

1. 更新完整 Run JSONB 快照；
2. 更新有顺序的消息记录；
3. 更新有顺序的 Trace 记录。

任一步失败，整个事务回滚，不留下“Run 已更新但 Trace 丢失”的半成品。

## 为什么不把所有候选和报价立即拆表

Agent 输出和候选结构还会随着长期记忆、RAG 和真实 Provider 接入继续变化。如果现在把每个嵌套字段完全关系化，每次小改动都会增加 migration 和多表拼装成本。

当前选择是：恢复所需数据先保留在版本化快照；只有已经明确需要独立查询的消息、Trace、租户、状态、草稿标识和版本进入列或单独表。以后出现稳定查询需求时再拆分，不丢失原始数据。

## 怎样防止跨租户读取

Repository 的 `get` 和 `list` 查询必须同时带 `tenant_id` 与 `user_id`。不存在的任务和属于别人的任务返回同一种拒绝结果，调用方不能通过错误差异判断另一租户的 Run 是否存在。

这是应用层第一道边界。生产强化阶段还会增加 PostgreSQL Row Level Security，防止未来某段 SQL 忘记租户条件；当前最小切片没有把 RLS 宣称为已完成。

## 怎样防止两个进程互相覆盖

每行有独立的 `lock_version`。Repository 读取任务时记住版本；保存时执行“只有数据库版本仍等于我读到的版本才更新”。

如果另一个进程已经先保存，版本就会变化，本次更新影响 0 行并明确报冲突。调用方必须重新读取和重新判断，不能静默覆盖较新的数据。这通常叫乐观锁，直白理解就是“写之前确认没有人抢先改过”。

## 怎样保证草稿不重复

数据库为 `draft_id` 和 `draft_idempotency_key` 建立唯一约束。即使两个应用实例同时越过进程内锁，数据库也只接受一个相同业务身份的草稿。服务端 HITL、报价重校验和 Action Token 仍然保留；数据库唯一约束是最后一道防重边界，不替代业务确认。

## 为什么用 Alembic

生产数据库不能靠应用启动时猜测并创建表。Alembic 把每次结构变化保存为有顺序、可审查的 migration，部署时先升级结构再运行新代码。`create_schema()` 只用于单元测试和本地快速验证，Compose 启动 backend 时执行 `alembic upgrade head`。

## 验证证据

- Repository 单元测试覆盖完整 Run、Message 和 Trace 往返；
- 跨租户查询返回统一拒绝；
- 两个旧版本写入者中的后者被拒绝；
- 重复草稿标识被唯一约束拒绝；
- PostgreSQL 17 从空库执行 migration 后，真实完成 start -> confirm -> draft；
- 数据库场景进入 deterministic 评测门禁。

## 当前限制

- 默认离线模式仍用 JSON，便于无数据库运行；配置为 `postgres` 或使用 Compose 才切换 PostgreSQL；
- 尚未启用 PostgreSQL Row Level Security；
- 尚未增加生产连接池、慢查询和连接健康指标；
- 长期记忆表和审计表已由后续 migration 增加；向量索引与制度文档表仍属于下一片；
- SQLite 用于快速 Repository 自动化测试，真实 PostgreSQL migration 与闭环另行实跑验证。

## 术语对照

- JSONB：PostgreSQL 可查询的 JSON 类型；这里主要作为完整任务快照。
- Transaction / 事务：多次写入要么全部成功，要么全部撤销。
- Migration：有版本号的数据库结构变更脚本。
- Optimistic lock / 乐观锁：更新前比较版本，发现别人已经修改就拒绝覆盖。
- Unique constraint / 唯一约束：由数据库保证某个业务标识只能出现一次。
