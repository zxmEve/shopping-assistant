# ADR-0013：制度知识独立版本化，并由全文检索提供引用

- 状态：已采用
- 日期：2026-09-09

## 要解决的问题

Policy-as-Code 能稳定计算允许、拒绝和审批路径，但只返回一个逻辑引用，无法向用户展示具体制度条款。把制度全文放进 Prompt 或长期记忆，会混淆企业知识与个人偏好，也无法可靠处理租户、版本和生效期。

## 决策

制度知识使用独立的 `KnowledgeDocument -> KnowledgeDocumentVersion -> KnowledgeChunk` 数据链路：

```text
管理员导入不可变原文
  -> 保留 SHA-256、制度版本和生效时间
  -> 清理页码/布局噪声，按标题和条款切块
  -> 管理员显式发布
  -> tenant + category + effective_at 预过滤
  -> PostgreSQL FTS 召回并确定性排序
  -> 返回版本化 citation
  -> 与 Policy-as-Code version 比对
```

只有 `KNOWLEDGE_STEWARD`、`PROCUREMENT_SPECIALIST` 或 `ADMIN` 能导入、发布和重建索引。普通员工只能在自己的可信租户上下文中搜索已发布且当前生效的条款。

RAG 只解释制度，不决定制度。Engine 仍调用确定性 Policy Service；检索引用只有在 `policy_version` 与可执行规则一致时才进入候选证据。一旦某租户已经发布受治理的制度知识，检索无答案、无当前有效版本或版本冲突都会安全停止并要求人工复核。未开始迁移知识库的租户继续使用既有 Policy-as-Code 引用。

## 为什么这样选择

1. **知识与记忆分离**：企业制度由治理角色发布，不能由用户 Consent 或 Agent 记忆写入。
2. **权限先于检索**：关系型查询先限制 tenant、品类、发布状态和生效窗口，再执行相关性计算。
3. **保留不可变原文**：清洗和切块不覆盖原文；原文哈希支持审计和重建索引。
4. **结构优先切块**：标题和编号条款优先于固定字符窗口，金额、否定词和审批角色不被改写。
5. **规则与解释一致**：文档版本不能覆盖或替代可执行政策版本，冲突是一票否决项。
6. **渐进启用**：只有已发布制度的租户进入 fail-closed 模式，避免空知识库阻断现有主链路。

## 被拒绝的方案

### 把制度写入长期记忆

拒绝。长期记忆的所有权、Consent、更新流程和制度治理完全不同，且个人偏好不能覆盖公司制度。

### 让 LLM 直接根据制度片段决定 ALLOW/DENY

拒绝。相同事实必须得到可复现的政策结果；模型只适合组织解释，不适合成为金额、权限和审批的唯一裁判。

### 只做向量检索

暂不采用。当前制度集较小且包含编号、金额、版本等精确词，先建立可解释的 FTS 基线；pgvector、RRF 和 rerank 在下一切片加入，并必须复用同一权限预过滤。

## 结果与限制

- 已有 PostgreSQL GIN FTS 索引、SQLite 可移植测试路径、管理员导入/发布/重建索引 API 和员工搜索 API；
- Engine 在推荐与确认写入前都会重新验证制度知识版本；
- 当前中文检索使用受控的拉丁 token 与 CJK unigram/bigram，尚未在真实企业制度标注集上校准；
- 尚未实现 PDF/DOCX 解析、表格专用切块、pgvector、RRF、cross-encoder rerank、知识审计表和管理后台；
- 当前只接入笔记本品类，扩展品类时必须提供对应 Policy-as-Code 版本映射。
