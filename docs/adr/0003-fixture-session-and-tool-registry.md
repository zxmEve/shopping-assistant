# ADR-0003：身份由服务端确认，Agent 只能使用明确允许的工具

- 状态：已采用
- 日期：2026-09-04
- 关联需求：IAM-01、IAM-02、IAM-03、HITL-01

## 先说结论

客户端可以提交采购需求，但不能自己声明“我是谁、属于哪个租户、使用哪个成本中心”。服务端先根据登录会话确认身份，再按角色决定 Agent 可以看到和执行哪些工具。没有登记的工具一律拒绝；创建草稿这类写操作即使有权限，也必须再次获得用户确认。

## 一个具体攻击例子

旧接口允许客户端发送：

```text
X-Tenant-Id: demo_cn
X-User-Id: employee_001
X-Cost-Center: rd_jakarta
```

这些 Header 只是客户端传来的文字。如果攻击者把它们改成另一个用户或租户，服务端直接相信，就可能读取别人的预算、制度或采购任务。

另一个风险是只在 Prompt 里写：“普通员工不能下单”。用户可以要求模型忽略这句话，网页商品描述也可能包含恶意指令。只要工具实际上仍提供给模型，模型犯错时就可能调用它。

所以身份和工具权限都不能只是对 Agent 的文字提醒，必须是服务端真正执行的限制。

## 我们想达到什么效果

1. 用户不能通过修改请求参数切换身份或成本中心。
2. 普通员工看不到审批、下单和支付工具。
3. Agent 或 Prompt Injection 不能给自己增加能力。
4. 读取工具和写入工具使用不同的风险控制。
5. Fixture 演示能够表现真实安全边界，同时诚实说明它不是生产登录系统。

## 比较过的做法

| 做法 | 好处 | 风险 |
|---|---|---|
| 直接相信客户端 Header | 开发最快，测试方便 | 任何调用方都能伪造身份，不能形成租户边界 |
| 在 Prompt 中告诉模型不要越权 | 实现简单 | Prompt 不是权限系统，模型错误或注入内容可能绕过 |
| 给模型所有工具，调用时再检查 | 能在最后一步拦截部分错误 | 模型仍能看到敏感能力，误调用面和信息暴露面更大 |
| 服务端身份 + 按角色裁剪工具 + 写操作确认 | 多一层配置，但边界明确 | 需要维护角色和工具登记表 |

## 最终选择及原因

### 1. Fixture 使用不可猜业务含义的会话 Token

演示请求发送 `Authorization: Bearer fixture-session-cn-employee-001`。服务端把这个 Token 映射到固定的 tenant 和 user，忽略客户端自行提交的身份和成本中心 Header。

为什么：即使是 Fixture，也应该模拟“身份来自认证层”这个真实边界，而不是让业务参数决定身份。

这里的 Token 只是离线演示凭证，不是生产认证方案。生产环境要替换为企业 OIDC/SSO。

### 2. 组织信息由企业 Gateway 查询

确认 tenant/user 后，再查询部门、成本中心、地区和角色。

为什么：身份回答“你是谁”，企业目录回答“你属于哪里、拥有什么角色”。两者分开后，客户端无法直接覆盖企业事实。

### 3. 建立 Tool Registry

Tool Registry 可以理解为服务端的“工具登记表”。每个工具记录：名称、用途、风险等级、允许角色和版本。

为什么：系统需要一个统一地方回答三个问题：这个工具是否真实存在、当前角色是否允许使用、它是读取还是写入。否则权限逻辑会散落在 Prompt 和业务代码中。

### 4. 没有登记的工具默认拒绝

例如 `place_order`、`pay_order` 和 `approve_requisition` 没有注册，因此任何角色都不能调用。

为什么：默认允许意味着每新增一个工具都可能意外扩大权限；默认拒绝则要求开发者显式说明它为什么存在、谁能使用。

### 5. 在模型调用前就裁剪可见工具

普通员工只看到其角色允许的工具。

为什么：调用时鉴权仍然必须保留，但提前隐藏无权工具能减少模型误选，也避免向用户或模型暴露不必要的能力。

### 6. 写操作需要权限和确认两个条件

`create_requisition_draft` 属于业务写入。角色允许只表示“这个用户有资格做”，Action Token 则表示“这个用户已经确认本次具体操作”。二者缺一不可。

为什么：有权限不等于用户已经同意当前金额和报价。

### 7. 提供“当前可用工具”查询接口

`GET /api/agent/tools` 只返回当前角色可见的工具。

为什么：它能让 UI、测试和面试演示直接证明权限裁剪结果，同时不会泄漏不可见工具列表。

## 实际调用过程

```text
Bearer Token
  -> 服务端解析 tenant/user
  -> 企业 Gateway 查询部门、成本中心和角色
  -> Tool Registry 找出当前角色可用工具
  -> Agent 只能看到这些工具
  -> 每次实际调用仍由服务端再次检查
  -> 写操作还必须验证用户确认
```

## 为什么不让 LLM 管权限

LLM 可以根据需求选择“需要查询目录还是预算”，但它不能决定自己拥有哪些权限。权限是企业事实和安全规则，必须由服务端代码决定。即使模型输出“管理员已批准”，也不会因此出现审批或下单工具。

## 这项决策带来的代价

- 新工具必须登记名称、风险和允许角色；
- 角色变化需要同步更新登记表和测试；
- Fixture Session 需要维护一组固定映射；
- 工具可见性检查和调用时检查存在少量重复，但这是有意的纵深保护。

## 测试如何证明它有效

- 伪造 `X-Tenant-Id`、`X-User-Id` 和成本中心不会改变服务端身份；
- 缺少或使用未知 Fixture Session 会被拒绝；
- 普通员工能看到创建未提交草稿工具，但看不到审批、下单和支付工具；
- 调用未注册工具会被拒绝；
- 角色不匹配时，即使工具已经注册也会被拒绝；
- 未确认的业务写入会被拒绝；
- 跨租户读取已有任务会被拒绝。

## 当前限制

- Fixture Session 不是生产登录系统，没有真实登录、过期、刷新、撤销和密钥轮换；
- 当前租户过滤还没有统一下沉到数据库 Repository；
- OpenAI Agent 层尚未把所有领域能力改成真正的 function tools，后续接入时必须复用同一 Tool Registry。

## 术语对照

- Tenant：企业或业务租户，不同租户的数据必须隔离。
- Gateway：访问企业目录、预算或制度的统一接口。
- Tool Registry：服务端工具登记表。
- Allowlist：明确写出允许什么；没有写出的默认不允许。
- BUSINESS_WRITE：会改变业务数据的操作，例如创建采购草稿。
