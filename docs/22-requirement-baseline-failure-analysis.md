# 需求评测16条失败的分析与修复

结论：14条是明确的实现缺陷；另外2条兼有预算口径澄清与实现缺陷。当前契约只存单件预算上限，因此总预算仍需追问，不自动除以数量。本次未改动60条用例、标准答案或评分器。

本轮结果为本地确定性解析器及校验器结果，不是大模型准确率，也不是完整采购成功率。工程标签尚未经过业务正式复核。

## 为什么不修改总预算两条的答案

`RequiredFieldPolicy`明确询问“单件预算上限”，领域对象是`unit_budget`，`RequirementSpec.budget.maximum`当前没有标记整批预算的结构。20台、整批160000元是否可视为单台8000元，是产品契约的选择，不能单凭数学除法改变其业务含义。

本次延续v1保守口径：保留总预算原文、追问单件上限；若用户同时明确给出单件预算则采用该明确值。切换为总预算时让旧单价失效，避免继续使用不再适用的单价。未来支持整批预算，应增加领域字段、成本约束和新的标签版本；不能回写本次标准答案提高成绩。

## 修复内容

1. GB优先于G匹配，要求单位后不接英文字母，保留存储标记和GTE/LTE上下界。
2. 识别“改成、最终、现在、以…为准”等明确数量更正，不简单选择最后一个数字；拒绝与明确数量矛盾的模型提议。
3. 保留用户明确币种，不再把美元写成人民币；后端检查币种与原文一致。保留币种不代表新增汇率换算，寻源仍需通过已有币种一致性检查。
4. 提取肯定的全新/翻新/二手条件，否定不能支持相反结论；补齐明确遗漏的成色要求，并将条件传入领域需求；保留英文证据兼容性。
5. 区分总额与单价；总额不能直接写入单件上限。删除旧单价时，只接受有原文位置和旧值依据的REMOVE操作，不放松其他悬空证据检查。

## 解释限制与下一步

本次定位使用了原有40条holdout，因此它已经是“已见回归集”，不能再作为独立盲测证明泛化能力。50条新增测试也是开发验证，不冒充新的盲测集。下一阶段应由独立业务样本建设并冻结新的留出集，完成预算口径复核，再显式运行真实模型。此次未修改Prompt，也没有调用付费模型。
