## 怎样比较“校验前后”

每条用例只发起一次模型调用，拿到结果后深拷贝，再调用`RequirementSpecService.validate()`，分别保存与评分。

- proposal：适配器完成结构化解析、兼容修复及版本元数据绑定后的模型提议；不是未经处理的原始字符串。模型原始输出另存`provider_output`。
- final：领域校验、原文证据位置修复、条件过滤、补齐、状态与追问重算之后的结果。校验抛错时，包括现有规则解析器重新生成并校验的兜底结果。
- 后端校验阶段没有再次调用模型，因此两阶段共用同一笔token；不能把总token乘二，也不能说“校验后token下降”。
- 主评分沿用v1：事实字段/值/操作符/强度、证据、缺失项、冲突、追问覆盖、状态、版本及指定delta字段。错误值不重复算成遗漏；额外断言另计。

### 归一化差异诊断，独立于主评分

v1评分器要求`Shanghai`/`Shenzhen`和小写系统名；模型输出的“上海”/“深圳”、`Linux`/`Windows`会被记作错误值。它们是规范表示问题，不能全部解释成理解错了业务含义。

本轮事后诊断只识别上述两个城市的白名单别名与操作系统大小写，同时要求字段、操作符和强度相同；不引入模糊语义裁判、不豁免证据/状态问题，也不改原报告或主分数。

| 诊断 | 校验前 | 校验后 |
|---|---:|---:|
| 严格错误中的上述等价表示差异 | 20 | 17 |
| 其余错误提取 | 1（0.60%） | 4（2.38%） |

该诊断不是重新宣布通过率；23条proposal证据不合格等问题仍然存在。后续应先明确领域规范值契约和别名政策，再版本化修改归一化层与评分器，不能回写本轮答案让主分数变好。

## 逐例结果与重点问题

完整24条对照及每条token、耗时见[CSV](../backend/evals/audits/requirement-holdout-v2-live/20261022T135239-22c85f553f/case-comparison.csv)。以下是从原始proposal/final直接观察到的重点，不把代码修复混入评测：

| 用例 | 观察到的问题 | 归因与后续方向 |
|---|---|---|
| 02 | 模型提取1.5TB为1536GB，后端删除存储下限 | 校验不能因有限的规则表达覆盖而丢掉合理语义；完善单位核验，无法验证时保留待确认状态 |
| 03 | 模型将0.5TB提取为500GB；项目标签按1024口径为512GB。后端删除该条件 | 模型单位口径错误与后端删除后的遗漏应分别记录；先明确TB/GB单位契约，再统一换算 |
| 04、05 | 模型识别当前数量9/11；校验拒绝后兜底误取背景数量30/40；04还把品类改成monitor | 当前要求与被否定/已完成背景没有被规则正确区分；兜底也需要质量和冲突保护，不能天然视为可信 |
| 08 | 模型提取“两年半保修”为30个月，后端删除保修条件 | 中文时长校验覆盖不足；保留未验证条件并追问，或扩展确定性换算 |
| 15 | 模型同时保留2TB下限与1024GB上限；后端删掉下限，冲突消失 | 冲突检查前过滤有效条件会掩盖冲突；应核验后保留双方证据 |
| 16 | 模型擅自把136000/17换成单台8000；后端正确拒绝，但兜底又漏掉内存和硬盘 | 预算安全规则有效；整份重建兜底损失其他正确字段，适合局部隔离与定向修复 |
| 19 | 模型已改成48GB内存，后端又加回16GB旧约束，且出现重复constraint_id | delta路径、约束ID与继承策略缺少统一契约；对变更字段做精确替换并检查唯一性 |
| 22 | 模型已清空被撤销的8000预算；delta证据/操作校验失败后，兜底恢复旧预算 | 撤销语义与delta协议需要校验和修复；撤销失败应保持待确认，不能静默恢复旧授权值 |
| 23 | 模型已改为2048GB，后端最终恢复旧1024GB | 多字段更新与旧快照合并存在覆盖副作用；需要用“未修改字段保持、已修改字段不能回滚”作为不变量 |
| 24 | 模型产生未经服务器授权的默认状态，后端拒绝，兜底最终正确表达内存不限 | 权限门禁有效；保留模型错误与兜底成功两个事实 |

delta路径既涉及模型输出协议，也涉及后端合并和评分器可识别的路径形式；不应未经契约审查就将全部delta不匹配都归因于模型语义错误。

建议下一步按“撤销旧值与错误恢复 → 背景误识别与兜底保护 → 单位/时长核验 → 规范值与delta契约”排序修复。修复时用当前集合做已见回归，另外冻结新盲测集；本次报告保持不变。
